# 飞书群里的管理端（在群里 @机器人 操作 /manage）

把 /manage 的全部操作搬到飞书群里：@机器人 发一条命令就能查数据、改数据。
**不需要打开网页。**

## 三个机器人/通道，别搞混

| 东西 | 能力 | 用在哪 |
|---|---|---|
| **群自定义机器人** webhook（`FEISHU_WEBHOOK_URL`） | **只能发** | 提交代理商申请 → 群里收提醒 |
| **自建应用**（`FEISHU_APP_ID` + `FEISHU_APP_SECRET`） | **能收能发** | 事件订阅到 `/api/feishu/events`，跑管理命令 |
| 部署告警（`deploy/feishu-alert.mjs`） | 单向 | 备份 / 自检 / CI 告警 |

**关键限制**：群自定义机器人的 webhook 是"只发"的，拿不到群里任何消息。
所以"在群里和机器人交互"这件事**不可能靠 webhook 实现**，必须用自建应用的
事件订阅（`im.message.receive_v1` + 卡片回调）。群里会显示成两个不同的机器人。

## 安全模型（改代码前先读这段）

`/api/feishu/events` 是一个**公网可访问的 POST 端点**，而它能执行管理员操作
（授予角色、删除用户、删活动、拉黑）。所以顺序是固定的：

1. **验签 + 时间窗** → 失败 401，且不回显原因（那是在送情报）
2. `url_verification` challenge（飞书后台保存请求地址时的握手）
3. **event_id 去重**（飞书在没收到 2xx 时会重投同一事件 → "点一下确认"会执行两次）
4. 分发：消息事件 / 卡片回调
5. **最后**才解析操作者

授权只看 `FEISHU_ADMINS` 白名单。**「在群里」不等于「有权限」** —— 群里任何人都能
@机器人，未授权者一律拒绝、不回显任何管理数据，只写审计。

五条容易被绕过、所以逐条钉死了的不变量：

| 不变量 | 破了会怎样 | 谁在守 |
|---|---|---|
| challenge 应答排在「未配置密钥 → 503」**之前** | 后台永远验证不通过（死锁） | drift-guard + 单测 |
| 握手走 `peekDecrypted`（只解密不验签），事件走 `parseInbound`（强制验签） | 反过来：没有密钥的握手过不去；放开则公网可伪造事件 = /manage 开放 | 同上 |
| `Math.abs(nowMs - tsMs) > MAX_CLOCK_SKEW_MS` | 抓包重放无限期有效 | 同上 |
| `seenEvents.has(eventId)` | 飞书重投 → 点一下执行两次 | 同上 |
| 两条入站路径各 `await resolveOperator(openId)` 一次 | 群里任何人都能点别人发出的确认卡片 | 同上 |

第六条是语义上的：`resolveOperator` 必须用 `getUserByEmail`（查）而不是
`ensureUser`（upsert）。用后者的话，白名单里写错一个邮箱就会**凭空造出一个账号**。

第七条针对的是「用户点两下」——那是两个不同的 `event_id`，去重挡不住，
所以确认卡片带**一次性 token**，执行前消费掉（见第七节）。

## 写操作为什么要二次确认

不是因为防攻击者（签名已经挡住了），而是防**误操作与被诱导**：
群里有人贴一段看起来像命令的文本、或者手滑多点一次，都不该立刻生效。
所以收到写命令只产生一张确认卡片，点按钮才执行；按钮回调同样验签、同样查白名单、
同样按 event_id 去重、同样消费一次性令牌。

`planWriteCommand` 里**不允许**出现任何写函数调用 —— drift-guard 会逐个点名检查
（`setUserRole` / `deleteUser` / `deleteActivity` / `reviewAgentApplication` …）。

## 业务逻辑不重写

命令层**调用与网页端完全相同的 `lib/server/*` 函数**。这不是洁癖：
审核动作（授予角色、删除用户）是不可逆的，两份实现迟早会漂移，
而且漂移之后没人记得。审计也走同一个 `writeAudit`，`detail` 里额外带
`via: "feishu"` 与操作者 open_id —— 审计日志 append-only，事后补不了。

## 命令表

**读**（直接回结果）

```
总览            活动 [slug]        用户        代理商
赛事            黑名单            审计 [条数]
```

**写**（回确认卡片，点按钮才执行）

```
公开 <slug>                 下线 <slug>              删除活动 <slug>
通过作品 <slug> <id>        驳回作品 <slug> <id>     撤回作品 <slug> <id>
刷新作品 <slug> <id>        移除报名 <slug> <userId>
代理商通过 <id> [备注]      代理商驳回 <id> [备注]
设为代理商 <userId>         设为用户 <userId>        设为管理员 <userId>
删除用户 <userId>           拉黑 <邮箱> <理由>       解拉黑 <id>
隐藏赛事 <id>               显示赛事 <id>           删除赛事 <id>
```

支持英文别名（`overview` / `agents` / `help` …）。
**不做模糊匹配**：拼错的词会落到"未知命令"而不是猜一个相近的写操作 ——
在管理命令上猜错代价比报错大得多。

## 刻意不做的事

- **审计日志在群里只给摘要**：IP / UA / 端口不在群里展示。群消息留在飞书侧、
  转发出去撤不回，而这些字段正是 8.4.3 可溯源三件套的一部分。
  要看全量请去 /manage。
- **不接受自由文本的任意 SQL 式操作**：命令是封闭枚举，不是 eval。
- **不在群里显示任何未授权者的 open_id**：写进审计日志，管理员自己查。

## 飞书后台配置（需要你做，代码这边已经就绪）

在**自建应用**的后台（不是群自定义机器人）：

1. **事件与回调 → 事件配置**
   - 请求地址：`https://hangkathon.com/api/feishu/events`
   - 订阅方式：把请求地址配置到开发者后台（收到 challenge 后会显示验证成功）
   - 添加事件：`接收消息 im.message.receive_v1`
2. **事件与回调 → 加密策略 → Encrypt Key**
   - 打开，取到字符串填进服务器 `/opt/hangkathon/.env` 的 `FEISHU_ENCRYPT_KEY=`
   - （选填）Verification Token 一并填上，便于日后排查
3. **权限管理**：`im:message`（接收 @机器人消息）、`im:message:send_as_bot`（发回复与卡片）、
   `card:write`（发交互卡片）。加权限后要**发布版本**才会生效。
4. **把应用拉进群**：应用没在群里就收不到消息。
5. 服务器 `.env` 加：
   ```
   FEISHU_ENCRYPT_KEY=<上面取到的>
   FEISHU_ADMINS=ou_你的openid=你的站内邮箱
   ```
   然后 `docker compose up -d` 重建（`.env` 不在 git 里，CI 不会覆盖它）。

## 三、怎么拿到自己的 open_id

两种方式，别选错：

1. **在群里 @机器人 发一条命令** —— 未授权时会回一条说明，
   同时把 open_id 记进审计日志（`category=security`、`action=feishu.bot.denied`）。
   这是最省事的方式。
2. 调 `GET /open-apis/im/v1/chats/{chat_id}/members` 直接列成员 ——
   但它需要额外权限（`im:chat:readonly` 等）。**不值得为此开权限**：
   方式 1 顺带就把入站链路也测了，方式 2 只是多一次往返。

读到 open_id 后写进服务器 `.env` 的 `FEISHU_ADMINS`：

```
FEISHU_ADMINS=ou_xxx=fangruhang@gmail.com|1479856809@qq.com|owu1v2fzojzqfqflaufogylpsgo@wechat.user
```

**一个 open_id 可以绑多个站内邮箱**（`|` 分隔）：飞书的消息事件里只有 open_id、
不返回邮箱，而且**反查不出是哪个站内账号**。同一个人往往有多个站内账号
（微信登录会合成一个），猜错的后果是用户再等一轮"还是不行"。
`resolveOperator` 逐个尝试，取第一个能解析成 admin 的。

**未配 `FEISHU_ENCRYPT_KEY` 时端点整体返回 503** —— 宁可不可用，
也不能无验签运行。

## 七、联调踩过的坑（2026-10-13 → 10-17）

这一节是这份文档里最有价值的部分。上面的设计都是**想明白了才这么写**的，
而下面七条是**写完了、跑起来才发现**的——它们的症状全都长得很像
（`200671` / `200672` / "没反应"），根因却各不相同。

**唯一的通用解法：把真实数据打出来。** 中途加的两行日志
（入站请求的形状、验签头的实际取值）价值超过我写的绝大部分代码。
连续三次靠"读代码推断"都判断错了，而日志一打出来就立刻清楚。

| # | 根因 | 表层症状 | 教训 |
|---|---|---|---|
| 1 | 握手排在 `requireEncryptKey()` 之后 | 后台报「返回数据不是合法的JSON格式」，**看着像 URL 不合法** | 握手是建立信任的第一步，不能排在它要用的密钥检查之后 |
| 2 | 加密后的握手**不带签名头**，而 `parseInbound` 是「先验签后解密」 | 401 / 200671 | 同上：握手不可能用还没建立的信任自证，所以改走 `peekDecrypted`（只解密不验签） |
| 3 | 到处是 `.catch(() => {})`，把回复失败吞干净 | 用户发了命令，机器人**一声不吭** | 改为 `bestEffort()`：不抛，但必须写日志。空 catch 只在"失败也不该影响主流程"且"日志本来就该静默"两处站得住 |
| 4 | 卡片没写 `"schema": "2.0"` | 标题能渲染、正文空白，**接口返回 code=0、零报错** | 飞书卡片有两套结构；不写 `schema` 时按 1.0 解析，`body.elements` 被整个忽略 |
| 5 | 2.0 里用了 `note` / `action` 标签 | 卡片 400（`cards of schema V2 no longer support this capability`） | 2.0 的元素在 `body.elements`、**没有**这两个标签：小字用 markdown、按钮直接挂在 elements |
| 6 | 卡片回调响应是空对象 `{}` | 200671 | 回调响应至少要带 `toast` 或 `card` 之一，所以做成必填参数 |
| 7 | **时间戳头有两种格式** | 200672 | 见下 |

### 时间戳有两种格式（最容易踩的一个）

同一个头、同一个厂商，两种完全不同的取值：

```
事件回调（收消息）    x-lark-request-timestamp: "1792132835"
卡片回调（点按钮）    x-lark-request-timestamp: "2026-10-16 14:41:47.224834685 +0800 CST m=+328043.243701041"
```

一直假设只有第一种，于是**所有卡片回调**被判「时间戳不是数字」→ 401 → 飞书显示 200672。
签名算法本身是对的（sha256、64 位十六进制，两边一致），错的只是这一项。

而且这种字符串**不能直接丢给 `Date.parse`**：V8 会把结尾的 `CST` 识别成
「美国中部时区 UTC-6」，`+0800` 被整个忽略，结果偏了 **14 小时**
（14:41+0800 应是 06:41Z，却算成 20:41Z）。
**解析失败会报错，而安静地算错只会让时间窗判断失真**——后者危险得多。
所以自己拆字段、拼标准 ISO 8601 再解析：数字偏移才是权威，时区缩写一律丢弃。

### 回调响应为什么不更新卡片

带 `card` 的回调响应会被判 200672（验签已通过、响应也送到了，是响应内容的问题）。
与其赌一个猜出来的格式，改成**只回 `toast`**——绝对合法的最小响应。

代价是按钮留在原地，于是补上一个更要紧的东西：**一次性令牌**。
`event_id` 去重挡不住「用户点两下」——那是两个不同的 event_id。
每张确认卡片带一个随机 token，执行前先消费掉，第二次只回提示不执行。
删除用户、删活动这类不可逆操作，不能指望用户只点一次。

实测：同一 token 第二次点 → 「这条确认已经处理过了，不会重复执行」；换新 token → 正常执行。
（证明不是笼统地全挡。）

## 八、实测过的行为（2026-10-17）

| 场景 | 结果 |
|---|---|
| 读命令 `总览` / `代理商` | 返回数据卡片 ✅ |
| 写命令 → 只生成确认卡片 | 数据库零变更 ✅ |
| 点「取消」 | 「已取消，没有执行任何操作」，零变更 ✅ |
| 点「确认执行」`下线 guoqing-77` | `public` → `unlisted`，审计 `feishu.下线` ✅ |
| 同一令牌点第二次 | 被挡，零变更 ✅ |
| 白名单外 open_id 发命令 | 拒绝，审计 `feishu.bot.denied`，**无任何管理数据泄漏** ✅ |
| 白名单外点确认按钮 | 「未授权，操作没有执行」，数据零变更 ✅ |
| 伪造签名 / 无签名头 | 401 ✅ |
| 超 5 分钟的重放 | 401（时间窗仍生效）✅ |
